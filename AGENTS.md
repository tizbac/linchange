# AGENTS.md

Repository-specific instructions and traps for coding agents.

## Docker package builds

`./package-docker.sh` builds the `.deb` entirely inside Docker. It has broken
several times after Angular dependency changes. There are two independent
traps; fix both before rerunning the script.

### Trap 1: Angular patch versions drift apart

Angular packages declare exact peer dependencies between each other.
`@angular/localize` peer-requires the **exact** `@angular/compiler` patch. If
`npm install @angular/localize` resolves a newer patch than the rest of
Angular (for example `localize@22.2.3` with `compiler@22.2.1`), the host may
tolerate it while the builder's `npm ci` fails with `ERESOLVE`.

**Rule:** keep every `@angular/*` package on the same patch. When adding one,
pin it to the version already used by the others, for example:

```bash
cd web
npm install --save-exact @angular/localize@22.2.1
```

### Trap 2: the lockfile and the builder's npm disagree

`web/package-lock.json` is generated by the host npm. The Dockerfiles install
npm explicitly (currently **npm 11.20.0**) because the npm bundled with
Node 22 resolves optional/peer bindings differently and rejects this lockfile
with errors such as:

```text
npm error `npm ci` can only install packages when your package.json and
npm error package-lock.json ... are in sync
npm error Missing: vite@8.3.5 from lock file
npm error Missing: @rolldown/binding-... from lock file
```

The `packageManager` field in `web/package.json`, the `npm install -g npm@...`
line in both `Dockerfile` and `Dockerfile.build`, and the npm that generated
the lockfile must stay in step.

**Rule:** after changing dependencies, regenerate the lockfile with the same
npm version the Dockerfiles use, not merely with whatever is in `node_modules`.
Verify with a clean `npm ci` in a container before running the packager.

## Checklist after changing `web/package.json`

1. Keep the `@angular/*` versions aligned.
2. Regenerate the lockfile:
   ```bash
   cd web
   npm install
   ```
3. Prove the lockfile is in sync with a **clean** install, not the existing
   `node_modules`:
   ```bash
   rm -rf /tmp/pkgtest
   mkdir -p /tmp/pkgtest/scripts
   cp package.json package-lock.json /tmp/pkgtest/
   cp -r scripts/* /tmp/pkgtest/scripts/ 2>/dev/null || true
   docker run --rm -v /tmp/pkgtest:/w -w /w node:22-alpine \
     sh -c 'npm install -g npm@11.20.0 >/dev/null 2>&1 && npm ci'
   ```
   If it reports `Missing: ... from lock file`, run the same npm version with
   `npm install --package-lock-only` in `web/` and repeat the clean check.
4. Build the web app and confirm both locale shells exist:
   ```bash
   cd web && npm run build
   test -f dist/linchange-web/browser/en/index.html
   test -f dist/linchange-web/browser/it/index.html
   ```
5. Run the packager:
   ```bash
   ./package-docker.sh
   ```
6. Confirm the package contains both shells:
   ```bash
   dpkg-deb -c dist/linchange_*.deb | grep 'web/.*/index.html'
   ```

Do not "fix" a lockfile problem with `npm ci --legacy-peer-deps` in the
Dockerfile. That hides an out-of-sync lockfile and produces a package whose
dependency tree was never the one in the repository.

## Read the first npm error, not the last

`package-docker.sh` ends with a long npm usage/help dump, which is noise. Search
the build log for the first real error:

```bash
./package-docker.sh > /tmp/opencode/docker-build.log 2>&1
grep -n "npm error code\|npm error Missing\|npm error ERESOLVE" /tmp/opencode/docker-build.log | head
```

- `ERESOLVE ... peer @angular/compiler@X` → align the Angular patch (Trap 1).
- `Missing: ... from lock file` → regenerate the lockfile with the Dockerfile's
  npm (Trap 2).
- `Application bundle generation failed` → run `npm run build` on the host
  first; the Docker failure is only a copy of a local Angular error.

## Web build output

The app is built for two locales with Angular's `@angular/localize`:

```text
web/dist/linchange-web/browser/en/...
web/dist/linchange-web/browser/it/...
```

There is deliberately no `browser/index.html`. Scripts that check for a built
app must look for `browser/en/index.html` (the e2e `stack.sh` does). The Go
server maps locale-less URLs to the preferred locale, and serves `/en/` and
`/it/` from those directories; the packager copies the whole `browser/` tree.

## Docker packaging files

- `package-docker.sh` — host-side entry point; builds and runs the packager
  image, copies the `.deb` into `dist/`.
- `Dockerfile.build` — Go + web build + `.deb` assembly.
- `Dockerfile` — the runtime image used by `docker compose`; it also builds
  the web app, so it needs the same npm pin as `Dockerfile.build`.
- `package.sh` — non-Docker packaging path; keep it consistent with the
  `Dockerfile.build` web output path.

## General conventions

- Do not reformat pre-existing gofmt offenders (for example
  `internal/smtpd/smtpd.go`, `internal/imapimport/*`) just because a change
  touched a nearby file.
- Prefer the `edit` tool for focused changes.
- After a feature: `go build ./...`, the relevant `go test` packages, and
  `cd web && npm run build`; run the Playwright suite with `npm run e2e` for
  UI changes.
- Commit each feature separately, as requested.
